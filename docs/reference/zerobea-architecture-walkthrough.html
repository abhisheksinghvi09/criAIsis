How the ontology grounds the agent (follow the dashed pink edges)

  • One registry, consulted four times. The Ontology Registry (concepts, domains, relationships) is the shared brain — it never sits in the request path, it's looked up at four points.
  • 1 · Intent — before any LLM call, deterministic concept-matching turns the user message into an OntologyIntentSignal (domain + confidence).
  • 2 · Grounding — that signal scopes the system prompt to the relevant domain's facts + proven strategies, with a confidence-aware routing instruction and a mandatory explainability footer. This is what keeps the LLM's answers grounded.
  • 3 · OBQC guard — when the agent calls a tool, the ontology validates it: SQL is restricted to ALLOWED_TABLES, blocking anything off-map.
  • 4 · Trait attribution — post-flight maps the tools used back to the 8 traits via IMPROVES_TRAIT.
  • Tools (bottom-right) are the handlers Claude can invoke — genealogy, KPI/analytics, commerce/catalog, traits/goals/campaigns — every call funneled through the middleware gates.
  • The 10 middleware hooks are collapsed here into 3 gate-groups (identity/scope → OBQC → budget/policy) for readability; diagram fidelity lives in tool_middleware.py.

03 Event-Driven Architecture & the Data Flywheel

Two stories on one canvas. Top — the event cascade: one order ripples through decoupled, idempotent consumers, each reacting and emitting the next event (Redis Pub/Sub locally, EventBridge in prod). Bottom — the flywheel: the closed loop that makes the AI measurably better over time — coaching is recorded, outcomes are detected 30/60/90 days later, correlated, and the strategies that actually worked are promoted back into the agent's prompts.

Top — why event-driven matters

  • Services never call each other directly. comp-engine emits order.created; it has no idea who's listening. Seven consumer queues fan out from the same events — add a new reaction by adding a consumer, nothing upstream changes.
  • Every consumer is idempotent (upserts, not inserts) so events can be safely re-delivered.
  • The cascade is real: order → volume aggregation → commission calc → commission.calculated + rank.changed → which simultaneously trigger AI agents, sync the Neo4j genealogy graph, and refresh analytics snapshots.
  • Transport flips by environment: Redis Pub/Sub locally, AWS EventBridge in production — per-event routing is configurable in the event_configs table.

Bottom — the flywheel is the moat

  • It closes the loop. Most AI systems give advice and forget it. Here every coaching action snapshots the user's baseline, then the system checks 30/60/90 days later whether rank, volume, retention, or traits actually moved.
  • Correlation, not just correlation-in-name: outcomes are scored with time-decay and genealogy-hop-decay so credit is attributed honestly. Only strategies with avg correlation ≥ 0.7 get promoted.
  • Promoted strategies are injected into the agent's prompt (the intelligence context, scoped to the resolved ontology intent) — so the next conversation literally coaches with what's proven to work.
  • Trait scores use logarithmic saturation — new = min(100, old + Δ·(1 − old/100)) — so early gains count, mastery is hard-won, and nothing runs away to 100.
  • Proven strategies can even auto-propose new ontology concepts (gated), letting the system's own vocabulary evolve from evidence.

What CatalogSync is for — in one line

  • The problem it solves: when an affiliate asks the AI "what's the PV on this product?" or "what should I recommend for dry skin?", the AI needs current product data. This workflow keeps that data fresh — automatically, every night.
  • 1 Fetch — pulls the product list from the company's catalog API (it adapts to any catalog format: a built-in NuSkin adapter or a generic field-mapping one).
  • 2 Normalize — standardizes every product into one shape (SKU, prices/PV/CV, category) so the rest of the platform doesn't care where it came from.
  • 3 Changed? — fingerprints each product and skips anything that hasn't changed since last run, so re-syncs are cheap.
  • 4 Index — new/updated products are embedded into the Knowledge Fabric (pgvector + OpenSearch hybrid search), which is what the AI searches at answer time.
  • The rest of the diagram: three worker processes / four task queues run ~18 other scheduled jobs the same way — content sync, outcome tracking, commission runs, graph sync, subscription forecasting — every schedule feature-flagged and tenant-aware.
